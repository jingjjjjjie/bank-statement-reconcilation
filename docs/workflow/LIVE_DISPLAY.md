# Live dashboard display

Display reads for workflow indicators, document status and matching use one in-memory
snapshot per active workspace. Concurrent requests share the same verification work.
The browser can request the previous display while a replacement is being prepared;
the header shows Updating... until the replacement completes. Normal requests wait
for invalidated snapshots to refresh.

Successful writes invalidate the snapshots. One server observer also checks saved
state, original sources and previews for filesystem changes every two seconds.
Metadata detects when to refresh a display; it does not establish source integrity.
Full snapshot builders continue hashing file contents. They run at least every
60 seconds while the read model is active, including when metadata is unchanged.
Workspace switches discard the previous workspace's cached display. Read failures
are reported rather than presenting the old snapshot as currently verified.

A single same-origin SSE connection per browser carries snapshot revisions and job
progress. Reconnects replay current revisions. Pages refresh only when their data
changes, and dirty drafts are preserved. HTTP progress polling remains the fallback
when the stream is unavailable. Matching is prepared in the background once workflow
readiness permits it; source previews remain separate, on-demand requests.

This cache is never used for approvals, extraction starts, exports or source-file
access. Those paths retain their existing current-evidence and revision checks.
No model requests or token usage are generated by display synchronization.

The cache is process-local: the first read after a server restart must still verify
its evidence. It is a display model, not an offline approval store or a new ledger.
